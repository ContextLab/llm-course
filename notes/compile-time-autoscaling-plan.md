## Executive Summary

The current slide scaling system uses runtime JavaScript (`autoscale.js`) which cannot affect PDF output. This causes HTML/PDF mismatch. This plan describes how to move all scaling logic to compile-time via `process_markdown.py` and predefined CSS classes in `cdl-theme.css`.

---

## 1. Analysis Phase

### 1.1 Current Architecture (BROKEN)

**Build Pipeline:**
```
lecture.md --> process_markdown.py --> temp.md --> Marp --> HTML + PDF
                                                    |
                                              [autoscale.js injected into HTML only]
```

**Why It Fails:**
- PDF is generated by Marp at compile time (no JavaScript)
- `autoscale.js` runs at page load in HTML only
- Result: HTML and PDF look different for dense slides

### 1.2 Existing CSS Scale Classes

The CSS already has compile-time scaling classes (from `cdl-theme.css`, lines 3148-3271):

| Class | Scale Factor | Use Case |
|-------|--------------|----------|
| `scale-90` | 0.90 | Content that almost fits |
| `scale-80` | 0.80 | Moderate density |
| `scale-78` | 0.78 | Two-column dense content |
| `scale-70` | 0.70 | Very dense content |

These classes correctly scale:
- h1 title (1.72em base)
- Body text (35px base)
- Flex container gaps
- Callout box fonts and padding

### 1.3 Elements That MUST NOT Be Scaled

- `.diagram-container` - SVG viewBox handles sizing
- `.chart-container` - Chart.js handles sizing
- Split tables (`.split-table`) - Already pre-sized at compile time
- Code blocks with line numbers - Already handled by `process_markdown.py`

### 1.4 Content Types Requiring Detection

| Content Type | Detection Method | Current Handling |
|--------------|------------------|------------------|
| Long code blocks | Line count | Split at 20 lines by `process_markdown.py` |
| Large tables | Row count | Split at 8 rows by `process_markdown.py` |
| Two-column layouts | `display: flex` divs | Runtime scaling by JS |
| Multiple callout boxes | Count of `.note-box`, etc. | Runtime scaling by JS |
| Nested lists | Depth of ul/ol nesting | Partial CSS handling |

## 2. Implementation Steps

### Phase 1: Enhance process_markdown.py for Content Analysis

**Goal:** Add a slide content analyzer that determines if scaling is needed BEFORE Marp compilation.

**Step 1.1:** Add slide parsing to `process_markdown.py`
- Parse markdown into individual slides (split on `---`)
- Track frontmatter and skip title slide

**Step 1.2:** Implement content density heuristics
```python
def estimate_slide_density(slide_content: str) -> dict:
    """
    Analyze slide content and return density metrics.

    Returns:
        dict with keys:
        - 'has_two_column': bool (flex container detected)
        - 'callout_count': int (number of callout boxes)
        - 'list_depth': int (max nesting level)
        - 'total_text_length': int (character count)
        - 'has_code_block': bool
        - 'has_table': bool
        - 'estimated_height': float (relative to slide height)
    """
```

**Step 1.3:** Create scaling decision function
```python
def determine_scale_class(metrics: dict) -> str | None:
    """
    Based on density metrics, return the appropriate scale class.

    Returns one of: 'scale-90', 'scale-80', 'scale-78', 'scale-70', or None
    """
    # Two-column with callout = typically needs 78%
    if metrics['has_two_column'] and metrics['callout_count'] >= 1:
        return 'scale-78'

    # Multiple callouts = needs 80%
    if metrics['callout_count'] >= 2:
        return 'scale-80'

    # Dense text content
    if metrics['total_text_length'] > 800:
        return 'scale-80'

    return None
```

**Step 1.4:** Inject Marp directive for scaling
When a scale class is determined, inject it as a Marp class directive:
```markdown
---
<!-- _class: scale-78 -->

# Slide Title
...
```

**Step 2.3:** Add table-specific scale classes

### Phase 3: Minimize autoscale.js

**Step 3.1:** Remove general content scaling
- Keep only the `hasCompileTimeScaling()` check
- Remove `layoutSlideContent()` - if no scale class, content should fit at default

**Step 3.2:** Keep only essential runtime features
- `detectWrappedColumns()` for tables (affects text alignment, not size)
- Chart animation replay (unrelated to scaling)
- Hash change handling for navigation

**Step 3.3:** Add validation warnings (optional)
```javascript
if (!hasCompileTimeScaling(slide) && contentOverflows(slide)) {
    console.warn(`Slide ${slideId} may need scaling class`);
}
```

### Phase 4: Update compile.sh Pipeline

**Step 4.1:** Add `--analyze` flag to process_markdown.py
Generate a report of which slides need scaling and why.

**Step 4.2:** Two-pass compilation option (optional)
1. First pass: Generate HTML, run analysis
2. Inject scale classes based on analysis
3. Second pass: Regenerate HTML and PDF

### Phase 5: Manual Override Support

**Step 5.1:** Authors can always manually add:
```markdown

```

**Step 5.2:** Add `<!-- no-scale -->` directive for opt-out

## 6. Content Detection Heuristics

### 6.1 Content Height Estimation

Since we cannot measure rendered height at compile time, use proxy metrics:

```python
# Approximate content units (each unit ~ 30px height)
CONTENT_WEIGHTS = {
    'h1': 3,
    'h2': 2.5,
    'paragraph': 1.5,  # per ~50 chars
    'list_item': 1.2,
    'callout_box': 4,  # includes title, padding
    'code_block_line': 0.8,
    'table_row': 1.5,
    'flex_container': 2,  # base overhead
}

# Slide height budget: ~15 units before scaling needed
```

### 6.2 Scale Class Selection

| Estimated Height | Scale Class |
|------------------|-------------|
| <= 15 units | None (default) |
| 15-17 units | scale-90 |
| 17-19 units | scale-80 |
| 19-21 units | scale-78 |
| 21-25 units | scale-70 |
| > 25 units | Warning + scale-70 |
